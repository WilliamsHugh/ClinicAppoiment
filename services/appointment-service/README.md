# Appointment Service — M2-BOOKING-001 (TV3)

The public request path is Gateway → Appointment Service → its own PostgreSQL database. Patient and Doctor references are checked through the owning services' internal HTTP APIs; this service never reads their databases.

Copy `.env.example` to `.env`, set `DATABASE_URL` to the Appointment database, and set the Doctor and User internal tokens. `USER_APPOINTMENT_INTERNAL_API_TOKEN` must match User Service's private Appointment caller credential. It is sent on every patient lookup, including outbox delivery; missing, rejected, or malformed lookup responses fail closed. Run `npm run db:migrate:appointment` at the repository root before `npm run dev:appointment`. The migration is repeatable and upgrades the scaffold tables without deleting appointments. It fails if legacy rows violate the new positive-interval or active-overlap constraints; resolve those rows explicitly before retrying.

The migration uses `btree_gist` and a GiST exclusion constraint on half-open ranges `[scheduled_start_at, scheduled_end_at)`. `PENDING`, `CONFIRMED`, and `CHECKED_IN` reserve the doctor; adjacent intervals and terminal rows do not conflict. Both creation and rescheduling use transactions. Creation stores the appointment, initial history, idempotency claim, and outbox event in one transaction. The idempotency key is scoped to `(actor_id, operation, key)` and the normalized booking payload; an exact retry returns the original appointment, while a changed payload returns `409`.

`GET /health` checks the database and migration version. The list endpoint filters and paginates in SQL with stable `(scheduled_start_at, id)` ordering. The internal occupancy endpoint reads the same persisted active appointments.

Run unit tests with `npm test -w @clinic/appointment-service`. To run PostgreSQL integration tests, provide a **disposable** database and set `APPOINTMENT_TEST_DATABASE_URL` plus `APPOINTMENT_TEST_DATABASE_DISPOSABLE=1`. Those tests apply the migration twice and truncate Appointment tables before testing concurrent overlapping creates and reschedules from independent pools, actor-scoped idempotency, replay after a new connection pool, history, occupancy, and rollback. They are skipped when no disposable test database is configured.

M2-BOOKING-002 (TV3) restricts patient access to the User Service profile linked to the actor and doctor access to the active Doctor Service profile linked to the actor. The Doctor lookup is `GET /internal/v1/doctors/by-user/{userId}` with the private `DOCTOR_INTERNAL_API_TOKEN`. STAFF and ADMIN can operate the contract's scheduling and reception routes; only the assigned DOCTOR can complete an appointment. Reschedule requires a future slot and `PENDING` or `CONFIRMED` status. State transitions are rechecked after locking the appointment row, so two concurrent commands cannot both advance from the same prior state.

The outbox writer is included so booking mutations are atomic. Processing, retry, and consumer delivery belong to M2-BOOKING-003. Gateway-to-service caller authentication remains a coordinated M2-PLATFORM-002 dependency; the Appointment role checks use identity that the Gateway must authenticate and forward.
